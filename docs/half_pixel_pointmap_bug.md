# 点图半像素 bug:主点 128 与 127.5 差半个像素

> 本文件是原机器 `~/knowledge/half_pixel_pointmap_bug/README.md` 的副本(2026-09-27)。文中 `~/tmp/…`、`~/knowledge/…` 等证据路径只在原机器上存在。

> **一句话**:数据加载器生成 3D 点图时,把像素的左上角当成了像素中心。所有真值点在 x、y 方向各偏 0.5 个像素。射线、渲染、深度指标都没错,错的只有点图这一处。修法:在 `pinhole_z_depth_to_xyz` 里给像素下标加 0.5,内参和射线都不要动。

**这个 bug 是什么。** 256 宽的图里,第 i 列像素的中心在 i + 0.5 处。模型算射线用 i + 0.5 − 128,加载器算点图用 i − 128,两者差 0.5 个像素。

**怎么查出来的。** 用真值深度把一张图的像素投到另一张图,再和那张图的深度比。按点图的写法(主点 128),"点落在对方表面前面"这种只有几何算错才会出现的情况占 3.23%;按射线的写法(主点 127.5)只占 1.49%。

**怎么算修好。** 修完后,点图上每个点都应落在模型为同一像素生成的射线上。修前每个点偏 0.71 个像素,修后是 0。`tools_s2/check_pointmap_on_ray.py`一条命令就能验收(第 7 节)。

写于 2026-09-27。起因:用户定"这是第一阶段的 bug,很多底座都有,统一修改"。本文所有行号都在 09-27 用 grep 对各仓工作树核过。

## 1. 先说清三个概念

**像素下标与连续坐标。** 像素下标是整数 0、1、2……。连续坐标把图像看成一块平面,第 i 列像素占 [i, i+1) 这一段。所以像素中心在连续坐标 i + 0.5 处,左上角在 i 处。

**主点。** 主点是相机光轴穿过图像的位置。我们的 Blender 相机没有偏移,主点就在图像正中。256 宽的图,正中在连续坐标 128 处,换成下标是 127.5。"128 还是 127.5"的争论,其实是同一个点在两种坐标下的写法。

**反投影。** 反投影是已知一个像素和它的深度,算出对应的 3D 点。做法是从相机中心出发,穿过这个像素,沿直线走到该深度。直线穿过像素的哪个位置,决定了点落在哪里。

## 2. bug 在哪:两段代码对照

加载器生成点图的函数(参考仓 `~/code/RnG_lagernvs`,分支 uni3t,`data/dataset_objaverse.py` 第 128–141 行):

```python
@staticmethod
def pinhole_z_depth_to_xyz(depth, f, H=512, W=512):
    ...
    y, x = np.mgrid[:H, :W]      # 整数下标
    x = x - W // 2               # 第 137 行:下标直接减 128
    y = H // 2 - y               # 第 138 行
    x = x / f * z
    y = - y / f * z              # y 取了两次负号,净结果 = (下标 − 128) / f × z
    return np.stack([x, y, z], -1)
```

模型生成射线的函数(同仓 `utils/data_utils.py` 第 73–74 行):

```python
x = (x + 0.5 - fxfycxcy[:, 2:3]) / fxfycxcy[:, 0:1]    # fxfycxcy[:, 2] = cx = 128
y = (y + 0.5 - fxfycxcy[:, 3:4]) / fxfycxcy[:, 1:2]    # fxfycxcy[:, 3] = cy = 128
```

射线穿过像素中心(下标 + 0.5)。点图穿过的是下标本身,也就是像素左上角。两者在 x、y 方向各差 0.5 个像素。

内参 `fxfycxcy = [f, f, W/2, H/2]`(同文件第 250–251 行)按连续坐标写,本身是对的。点图函数没有读这组内参,自己写了一个 `W // 2`,错在这里。验证集加载器 `data/dataset_gso_ours.py::GSODataset_ours` 继承了同一个函数,所以训练集和验证集的点图都偏。

## 3. 偏多少:公式、小例子、实际大小

白话:同一个像素,点图给的点和正确的点深度相同,只是横向错开半个像素。换成 3D 距离,就是"半个像素在这个深度处有多宽"。物体越远、焦距越短,这个宽度越大。

```
正确(过像素中心):  X = (i + 0.5 − W/2) / f × z      Y = (j + 0.5 − H/2) / f × z
现状(过左上角):    X = (i − W/2) / f × z            Y = (j − H/2) / f × z
误差(现状 − 正确): ΔX = ΔY = −0.5 / f × z          合计长度 = 0.71 / f × z
```

字母表:

- `i`、`j`:像素的列下标、行下标。整数,自变量,范围 0 到 W−1、0 到 H−1。
- `W`、`H`:图像宽、高,单位像素。常数,我们的底座是 256 或 448。
- `f`:焦距,单位像素,x、y 两方向相同。由 `f = (W/2) / tan(fov/2)` 算出。fov 逐帧读自 transforms.json,没有时取 40°。09-27 实测 256 图:v1 验证集 fov 27°–70°(f 中位数 254),all287k 训练集 41°–71°(f 中位数 259)。
- `z`:该像素的 z 深度,即点沿相机光轴方向的距离。场景已按第一张图的相机距离归一。实测前景 z 的中位数:验证集 0.87,训练集 0.83;5–95 分位约 0.62–1.13。
- `X`、`Y`:点在相机坐标系下的横、纵坐标。约定同 OpenCV:x 向右,y 向下,z 向前。
- `ΔX`、`ΔY`:现状减正确。负号表示点偏向像素的左、上方。
- `0.5`:像素中心相对左上角的偏移,单位像素。
- `0.71`:两个方向合起来的偏移,即 √(0.5² + 0.5²),单位像素。

**能口算的小例子**(一维,图宽 4 个像素):

- 设 W = 4,f = 2,物体是一面 z = 2 的平墙。主点在连续坐标 W/2 = 2 处。
- 理想情形:第 0 列像素的中心在 0.5。X = (0 + 0.5 − 2) / 2 × 2 = −1.5。投回图像:u = f × X / z + 2 = 2 × (−1.5) / 2 + 2 = 0.5,正好回到像素中心,误差 0。
- 现状:X = (0 − 2) / 2 × 2 = −2.0。投回图像:u = 2 × (−2.0) / 2 + 2 = 0,落在像素左边缘。
- 差距:3D 里差 −2.0 − (−1.5) = −0.5,等于 0.5 × z / f = 0.5 × 2 / 2。图像上差 0.5 个像素。

**实际大小**:

| 数据(256 图) | f 中位数 | z 中位数 | 每个方向的 3D 误差 | 两方向合计 |
|---|---|---|---|---|
| v1 验证集(GSO,前 16 个物体 × 14 张) | 254.0 | 0.873 | 1.72e-3 | 2.43e-3 |
| all287k 训练集(前 16 个物体 × 10 张) | 259.4 | 0.828 | 1.60e-3 | 2.26e-3 |

表注:

- 3D 误差 = 0.5 / f × z,代入该行的 f、z 中位数。例:0.5 / 254.0 × 0.873 = 1.72e-3;合计再乘 √2。
- 单位是"第一张图的相机到原点的距离"。若把这个距离当 1 米,每个点在每个方向偏约 1.7 毫米。
- 像素口径与分辨率无关,每个方向恒为 0.5 像素。448 图在同样视场下焦距是 256 图的 1.75 倍,3D 误差是 256 图的 0.57 倍。
- f、z 由 09-27 用 `RnG_lagernvs_stage2` 的 uni3t 配置读数据实测(roll 设 0)。

**体感对照**:第一阶段模型 `PLN2uni3t_all287k_b32t6_fp32lr35_wsd60k_a10k` ckpt_70000 在 subset64 上,预测点投到输入图的误差均值是 2.81 像素(有位姿)。点图真值自带的偏差投到输入图后,均值是 0.53 像素,约占前者的五分之一(证据 D)。

## 4. 影响什么、不影响什么

| 部分 | 受影响吗 | 为什么 |
|---|---|---|
| 射线与新视角渲染(PSNR / LPIPS) | 否 | 射线用像素中心;渲染不读点图 |
| 深度指标(abs_rel 等) | 否 | 只比 z(`utils/metric_utils.py:232-244`);横向错开不改变 z |
| 位姿与位姿指标 | 否 | 相机头的真值来自 c2w,不经过点图 |

| 点图可视化(`viser_compare.py` 等) | 是,只影响显示 | 同一写法 |
| 第二阶段的几何窗口 | 是 | 用第一阶段预测的点做投影;用户 09-26 定暂不改 |

表注:"受影响"指结果里含有这 0.5 像素。点图损失里的法向项由相邻点之差算出,整体平移只带来二阶变化;这一条是推断,没有单独测。

## 5. 怎么修,以及不要怎么修

**只改一处:`pinhole_z_depth_to_xyz` 里的两行。**

```python
# 修前
x = x - W // 2
y = H // 2 - y
# 修后:像素 (j, i) 从它的中心 (i + 0.5, j + 0.5) 反投影
x = x + 0.5 - W / 2
y = H / 2 - (y + 0.5)
```

- 等价写法:`x = x - (W - 1) / 2`,`y = (H - 1) / 2 - y`。
- 下面两行 `x = x / f * z`、`y = - y / f * z` 不动。改完后 Y = (j + 0.5 − H/2) / f × z,与射线一致。
- 两行必须一起改。只改 x,y 方向仍偏 0.5 像素。

**不要这样修:**

1. **不要把内参 cx、cy 改成 127.5。** `compute_rays` 用 `int(2 * cy)` 反推图像尺寸(`utils/data_utils.py:56-57`),会得到 255 而不是 256。它随后算出的缩放值只赋给了局部变量,没有被用上(第 62–66 行)。于是射线直接用 cx = 127.5,变成 x + 0.5 − 127.5,原本正确的射线反而偏了半像素。点图函数根本不读 cx,原 bug 还在。
2. **不要改射线。** 射线是对的,证据 A、C、D 都指向像素中心。
3. **不要顺手改深度图的缩放方式。** 那是另一个独立的 0.25 像素偏移,改它会改变深度真值和掩码,见第 10 节。

**同一底座里可以一起改的地方**(都只影响显示或未被使用):

- `viser_compare.py` 第 62–63、132–133 行,`viser_compare copy.py` 同位置:可视化脚本,同一写法。
- `data/dataset_co3d.py:34`:自带一份反投影(用 K⁻¹ 乘整数下标),没有任何配置用到这个类。

## 7. 修完怎么验收

脚本:`tools_s2/check_pointmap_on_ray.py`。

- **它做什么。** 取验证集前 2 个物体,对每张图的每个前景像素,比较点图上的点和仓库自己的 `compute_rays` 为同一像素生成的射线,报点偏离射线多少像素。
- **为什么这样验。** 射线代码是模型实际使用的,三组证据都说它对。检查只经过数据集读出点图,不调用、不复制被改的函数,所以结论不会按构造恒真。
- **怎么算过。** x、y 两个方向偏差的中位数,以及合计偏差的 99 分位,都小于 0.001 像素。

```bash
cd ~/code/<某个底座>          # 在仓库根目录跑,CPU,几秒钟
export PYTHONNOUSERSITE=1 PYTHONDONTWRITEBYTECODE=1 OMP_NUM_THREADS=2 MKL_NUM_THREADS=2
PY=/mnt/data-alpha-sg-01/team-camera/home/z50057756/conda/envs/rng-fa3/bin/python
$PY tools_s2/check_pointmap_on_ray.py --config configs/<该仓的配置>.yaml
# 不改文件、先预览修复效果(只在内存里替换函数):
$PY tools_s2/check_pointmap_on_ray.py --config configs/<该仓的配置>.yaml --preview_fix
```

09-27 实测(`RnG_lagernvs_stage2`,uni3t 配置;另把同一配置的图像尺寸改成 448 再跑一遍,结果相同):

```
修前: dx median -0.5000 | dy median -0.5000 | |offset| median 0.7071 p99 0.7071  → FAIL(退出码 1)
修后: dx median -0.0000 | dy median -0.0000 | |offset| median 0.0000 p99 0.0000  → PASS(退出码 0)
```

- `dx`、`dy`:点相对该像素中心射线的偏移,单位像素,负号表示偏左、偏上。
- `|offset|`:两方向合计的偏移。

读法:

- 仍是 −0.5 / −0.5:改动没生效。检查是否改错了文件,或者跑的是另一个仓。
- 变成 +0.5:加反了符号。
- 只有一个方向是 0:只改了一行。
- `--split train` 可改查训练集。旧配置里的数据路径若已失效,换一个路径有效的配置即可,点图代码与配置无关。

## 8. 修完后新旧结果怎么比

- **新视角指标、深度指标、位姿指标:新旧可以直接比。** 评测不读点图,旧 ckpt 在修后的代码上评测,数字不变。修复只通过训练时的点图损失改变模型,改变量照常按 LPIPS 0.003 信号线判。
- **点图损失曲线(W&B 里的 point loss):新旧不能比绝对值。** 真值换了,曲线的零点跟着变。
- **旧 ckpt 续训:** 点图头要把输出挪半个像素。建议在跑的臂(例如 α 臂)中途不换加载器;新开的臂一律用修后版本;同一个臂前后必须用同一版本。
- **旧 ckpt 做下游:** 例如第二阶段冻结的 `PLN2uni3t_all287k_b32t6_fp32lr35_wsd60k_a10k` ckpt_70000。它按偏的真值训练,预计输出的点同样偏向左上角 0.5 像素。这一条是推断,没有直接测过模型输出的平均偏移。
- **第二阶段:** 用户 09-26 定暂不改,把第一阶段的点当作像素中心的点用(`model_s2/geometry.py` 顶部注释)。第二阶段的点图损失仍读加载器的点图(`model_s2/stage2_wrapper.py:148`)。若以后在 stage2 仓修加载器,第二阶段开局的点就会与新真值差半个像素,需要同时换一个用修后加载器训练的第一阶段。

## 9. 证据(四组实验,按从硬到软排)

先给分层:

- **最硬**:两段代码并排,差 0.5 一眼可见;加载器点图与"主点 128 的反投影"最大差 7.1e-8(浮点舍入级);第 7 节脚本修前恰为 −0.5000 / −0.5000。
- **中等**:三套数据、三个独立实现(A、C、D)都显示像素中心约定更自洽。
- **最软**:颜色一致性对主点不敏感(证据 B),只能排除偏离较大的取值。

下面的指标都用同一个定义:

- **不可能违例**:把视角 i 的前景像素按真值深度反投影,投到视角 j,若这个点比 j 看到的表面还靠前 1% 以上,就算一次违例。遮挡只会让点落在表面后面,所以这类点只能来自几何算错。越低越好。1% 容差是 09-24 计划定的。
- **深度误差中位数**:投过去的点的深度与 j 的真值深度的相对差,取中位数。只统计两相机夹角 < 60° 的视角对,避开遮挡造成的合法大误差。越低越好。

### 证据 A:真值几何自洽检查(09-24/25,job 在 CPU 分区)

**为什么做。** 注意力几何探针要用真值深度算像素对应,先要确认投影约定对不对。

**做了什么。**

## 10. 相关但独立的两个小偏移(可选修)

### 10.1 深度图与前景掩码的最近邻缩放:比 RGB 偏 0.25 像素(256 图)

**是什么。** 渲染图是 512 像素,加载器把它缩到 256。RGB 用 LANCZOS 缩放(第 224 行),深度和前景掩码用最近邻(NEAREST,第 235、284 行)。最近邻缩放是"每个输出像素直接照抄原图的某一个像素"。

**偏多少。** PIL 的最近邻给输出像素 i 照抄原图第 2i + 1 个像素。它的中心在原图连续坐标 2i + 1.5 处,换到输出图是 i + 0.75。输出像素 i 的中心在 i + 0.5,所以深度和掩码比 RGB 往右下偏 0.25 像素。LANCZOS 按中心对齐,RGB 没有这个偏移。

09-27 用 PIL 10.0.1 实测(本机 rng-fa3 环境):

- 512 → 256:每个输出像素都取原图 2i + 1,偏移恒为 +0.25 像素。
- 512 → 448:平均偏移 +0.0625 像素,逐列在 −0.31 到 +0.44 之间周期变化。
- LANCZOS 512 → 256:在线性斜坡图上偏移为 0。

这正好解释了证据 B 的几何最优点为何在 127.25。

**修完主 bug 后的残差。** 点已在正确的射线上,但深度取自 0.25 像素之外。表面正对相机时没有误差,表面越斜误差越大:

```
沿射线的深度误差 ≈ 0.25 / f × z × tan(θ)
```

字母表:

- `0.25`:深度样本相对像素中心的偏移,单位像素(256 图)。
- `f`:焦距,单位像素(v1 验证集中位数 254)。
- `z`:该像素的 z 深度(验证集前景中位数 0.87)。
- `θ`:表面法向与视线方向的夹角,0° 表示表面正对相机,越接近 90° 越斜。
- 左边:点沿射线方向偏离真实表面的距离,单位同 z。

例:θ = 45° 时 tan θ = 1,误差 = 0.25 / 254 × 0.87 = 8.6e-4,是主 bug 单方向误差(1.72e-3)的一半。θ = 0° 时误差为 0。

**建议:这次不改。**

1. 改它会改变深度真值和前景掩码。所有深度指标、依赖掩码的损失与前景指标都要重跑基线,新旧结果不能再比。
2. 修完主 bug 后,残差只出现在斜面上,且不超过主 bug 的量级。

**若以后要改。** 按 2×2 块处理:块内 alpha 平均 ≥ 0.5 算前景;深度取块内前景像素的均值或最小值。这个方案没有实现、没有测。不建议把反投影改成 i + 0.75:点会落在真实表面上,但离 RGB 像素中心横向差 0.25 像素,又回到本 bug 的形态。

### 10.2 CO3D 转换的主点取整:逐场景 ±0.5 像素以内

**是什么。** CO3D 转成 GSO 格式时,要把图贴进正方形画布,使主点落在画布中心(`scripts/convert_co3d_to_gso.py:189-195`)。贴图位置用 `int(round(cx))` 取整,主点因此偏离画布中心,偏差在 ±0.5 像素以内。

**影响。** 偏差方向逐场景不同,不形成统一方向的偏移,只影响 CO3D 转换数据。`~/knowledge/co3d_to_gso_conversion.md` 实测主点在图像中心 ±0.5 像素内。没有核实 CO3D 原始 cx 用的是下标还是连续坐标;若是下标,还会多出一个固定的 0.5 像素。

**建议:不改。** 若要精确,把 `cx − round(cx)` 的残差写进 transforms.json,再让加载器读取。

## 12. 收尾

**一句话。** 点图反投影少加了 0.5:把 `x = x - W // 2` 和 `y = H // 2 - y` 改成 `x = x + 0.5 - W / 2` 和 `y = H / 2 - (y + 0.5)`,内参与射线不动,验收脚本打出 0.0000 就算修好。

**成立的:**

- 点图每个方向偏 0.5 像素,偏向左上(代码对照;验收脚本修前恰为 −0.5000 / −0.5000)。
- 射线、渲染、深度指标、位姿都不受影响,新旧可比。
- 所有 `weight_point > 0` 的训练都学了偏的点:uni3t 系、RnG 系、CO3D 微调。

**不成立、已作废的:**

- "lagernvs 训练不用点图,所以不影响模型":只对 `weight_point = 0` 的臂成立。
- "把 cx 改成 127.5 就能修":会把原本正确的射线改坏,点图也不会变。
- "VGGT 腿在 v4 渲染上也核对过":只核对了 v2。

**待定、没测的:**

- 深度与掩码的 0.25 像素最近邻偏移、CO3D 取整:这次不改(第 10 节)。
- 旧 ckpt 预测的点实际平均偏多少:推断约 0.5 像素,没有直接测。

**哪步卡了从哪步再拆:**
